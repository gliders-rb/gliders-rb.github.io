# Adapters

> Optional gems that export field_struct classes to JSON Schema, Avro and Protobuf, trace actionable with OpenTelemetry, and expose actions as LLM tools.

An adapter is an optional gem on top of `field_struct` or `actionable`, and it handles one format. None is released yet, so each example here runs against the code in this repository. Unreleased All the adapters are at `1.0.0.pre1`. Protobuf and tools are previews. Their specs settle the behaviour, but none of it has shipped. ## Choose an adapter [Section titled “Choose an adapter”](#choose-an-adapter) | You want to | Adapter | Gem | | --------------------------------------------------------------- | ----------------------------------------------- | -------------------------- | | publish a struct’s JSON as a schema, for docs or other services | [JSON Schema](/adapters/json-schema/) | `field_struct-json_schema` | | write structs as Avro binary and read old events | [Avro](/adapters/avro/) | `field_struct-avro` | | encode Avro faster, with an optional Rust encoder | [Avro native encoder](/adapters/avro-native/) | `field_struct-avro-native` | | print a `.proto` and encode structs with Protobuf | [Protobuf](/adapters/protobuf/) (preview) | `field_struct-protobuf` | | trace action runs | [OpenTelemetry](/adapters/opentelemetry/) | `actionable-otel` | | let a language model call an action | [LLM and MCP tools](/adapters/tools/) (preview) | `actionable-tools` | ## Install [Section titled “Install”](#install) Every adapter is a separate gem, and you load it with an explicit `require`. 
```ruby
gem 'field_struct-json_schema'   # require 'field_struct/json_schema'
gem 'field_struct-avro'          # require 'field_struct/avro'
gem 'field_struct-protobuf'      # require 'field_struct/protobuf'
gem 'actionable-otel'            # require 'actionable/otel'
gem 'actionable-tools'           # require 'actionable/tools'
```
 Some pull in a library and some leave that to you. Avro depends on `avro` and Protobuf on `google-protobuf`. OpenTelemetry depends on `opentelemetry-api` alone, so the SDK and the exporter are your choice. The tools adapter needs `mcp` or `ruby_llm` only for the wrapper you require. ## How they behave [Section titled “How they behave”](#how-they-behave) * **Module functions first.** Each adapter works as plain functions, like `FieldStruct::Avro.schema(Hut)`, and has an opt-in `Methods` module for when you want `Hut.to_avro_schema` on the class. * **Requiring leaves your classes alone.** OpenTelemetry is the exception: `require 'actionable/otel'` turns tracing on. * **One shape, many formats.** The three format adapters share a single walk over a struct’s fields, [`FieldStruct::Introspection`](/adapters/introspection/). Output names come from `serialize`, so one declaration can call a field something different in `:json`, `:avro` and `:protobuf`. * **They refuse rather than approximate.** If a format can’t hold something exactly, the adapter raises, or leaves it out and documents that. 
```ruby
require 'field_struct/json_schema'


class Hut < FieldStruct::Base
  required :name, :string
end


Hut.respond_to?(:to_json_schema)                  # => false
FieldStruct::JSONSchema.generate(Hut)['required'] # => ["name"]


class Hut
  include FieldStruct::JSONSchema::Methods
end


Hut.respond_to?(:to_json_schema)                  # => true
```
 ## Go further [Section titled “Go further”](#go-further) * [How adapters work](/adapters/how-adapters-work/): why they are separate gems, and why they never approximate * [Introspection reference](/adapters/introspection/): the walk all the format adapters share * [Build your own adapter](/adapters/build-your-own/): a generator for another format in about 60 lines ## See also [Section titled “See also”](#see-also) * [How the two gems fit together](/explanation/how-the-gems-fit/) * [Introspection and tooling](/reference/field-struct/introspection-and-tooling/)

# Avro

> Write structs as Avro binary, read dispatches saved with an older class, and get an error where a value would have been rounded.

`field_struct-avro` maps a struct to an Avro record schema, an instance to a datum or to Avro binary, and bytes back to an instance. That includes bytes an older version of the class wrote. 
```ruby
gem 'field_struct-avro'
```
 
```ruby
require 'field_struct/avro'
```
 The unit of work is one datum. Container files, a schema registry and Avro JSON are all out of scope, and so is validation (`format:`, `in:`), which stays with the struct. If Avro has no exact way to hold a value, you get an `ArgumentError` instead of a rounded number. ## The schema of a struct [Section titled “The schema of a struct”](#the-schema-of-a-struct) 
```ruby
require 'field_struct/avro'


module Signals
  class Dispatch < FieldStruct::Base
    required :id, :uuid
    required :lamp, :symbol, enum: %i[fixed flashing]
    required :swell, :big_decimal, round: 2
    required :sent, :time, zone: 'America/Denver'
    optional :channels, :array, of: :string
  end
end


schema = FieldStruct::Avro.schema(Signals::Dispatch)
schema['name']                  # => "Dispatch"
schema['namespace']             # => "Signals"
schema['fields'].map { |f| f['name'] }   # => ["id", "lamp", "swell", "sent", "channels"]
schema['fields'][1]['type']     # => {"type"=>"enum", "name"=>"Dispatch_lamp", "symbols"=>["fixed", "flashing"]}
schema['fields'][2]['type']     # => {"type"=>"bytes", "logicalType"=>"decimal", "precision"=>38, "scale"=>2}
schema['fields'][4]['type']     # => ["null", {"type"=>"array", "items"=>["null", "string"]}]
```
 The mapping holds on to as much as Avro allows. Integers become `long`, never `int`. A decimal that has a scale (from `round:`) becomes an Avro `decimal`, and times keep every sub-second digit. A symbol with `enum:` turns into an Avro `enum`. Optional fields are unions with `null`. Array items are always nullable too, because a struct lets `nil` elements through. | Field type | Avro | | ------------------------------------- | ------------------------------------------------------------- | | `:integer` | `long` | | `:float` | `double` | | `:string`, `:email`, `:url`, `:value` | `string` (`:value` holds JSON text) | | `:uuid` | `string` with `logicalType` `uuid` | | `:binary` | `bytes` | | `:big_decimal` | `decimal` with the field’s scale, or `string` with no scale | | `:date` | `int` with `logicalType` `date` | | `:time`, `:datetime` | `long` with `timestamp-micros`, `-nanos` or `-millis` | | `:symbol` with `enum:` | a named `enum`; otherwise `string` | | arrays | `array`, items nullable | | nested structs | a named `record`, referenced by full name after its first use | A field with a usable default is not nullable, and the schema carries that default. A default Avro can’t write (a date, a decimal, a lambda) stays out of the schema, and the struct fills it in on read. Each `schema` call gives you a fresh copy. For `Signals::Dispatch.to_avro_schema`, `#to_avro` and `Signals::Dispatch.from_avro`, include `FieldStruct::Avro::Methods`. ## Use case: send a signal, read it back [Section titled “Use case: send a signal, read it back”](#use-case-send-a-signal-read-it-back) Say a lighthouse sends a dispatch to the harbor office. `encode` writes one datum as Avro binary, and `decode` reads it into a struct of whichever class you name. 
```ruby
dispatch = Signals::Dispatch.new(id: '3c5e7a10-92b4-4f6d-8e21-0a7d5b9c1e44', lamp: :flashing, swell: '2.75',
                                 sent: '2026-07-01T08:00:00', channels: %w[ch-16 ch-9])


bytes = FieldStruct::Avro.encode(dispatch)
bytes.encoding                                # => #<Encoding:BINARY (ASCII-8BIT)>
back = FieldStruct::Avro.decode(Signals::Dispatch, bytes)
back == dispatch                              # => true
back.sent.utc_offset                          # => -21600
```
 The field’s `zone:` puts the offset back on the way in. When all you need is the Hash the `avro` gem reads and writes, call `to_datum` and `from_datum`. 
```ruby
datum = FieldStruct::Avro.to_datum(dispatch)
datum.keys                                                       # => ["id", "lamp", "swell", "sent", "channels"]
FieldStruct::Avro.from_datum(Signals::Dispatch, datum) == dispatch   # => true
```
 ## Use case: read old signals after a class changes [Section titled “Use case: read old signals after a class changes”](#use-case-read-old-signals-after-a-class-changes) A dispatch logged last month predates two fields the class has since gained. Hand `decode` the schema those bytes were written with, as `writer_schema:`. A Hash, a JSON String or a parsed `Avro::Schema` all work. Avro pairs records by name, so the old schema must carry the namespace of the class doing the reading. 
```ruby
module Gen1
  class Buoy < FieldStruct::Base
    required :serial, :integer
  end
end


module Gen2
  class Buoy < FieldStruct::Base
    required :serial, :integer
    optional :callsign, :string
    required :moored, :date, default: Date.new(2026, 3, 14)
  end
end


old_bytes = FieldStruct::Avro.encode(Gen1::Buoy.new(serial: 31))
old_schema = FieldStruct::Avro.schema(Gen1::Buoy).merge('namespace' => 'Gen2')


buoy = FieldStruct::Avro.decode(Gen2::Buoy, old_bytes, writer_schema: old_schema)
[buoy.serial, buoy.callsign, buoy.moored]   # => [31, nil, Date.new(2026, 3, 14)]
```
 A field the writer never had gets the struct’s own default, even one Avro can’t express, like a date. ## It raises rather than lose data [Section titled “It raises rather than lose data”](#it-raises-rather-than-lose-data) A time carrying nanoseconds does not fit `timestamp-micros`. Rounding would change the value, so the adapter stops and tells you what to do about it. 
```ruby
class Roster < FieldStruct::Base
  required :keeper_name, :string
  required :logged, :time
  serialize :avro, keeper_name: 'keeperName'
end


entry = Roster.new(keeper_name: 'Odd', logged: Time.utc(2026, 10, 25, 21, 55, 12, Rational(123_456_789, 1000)))


begin
  FieldStruct::Avro.encode(entry)
rescue ArgumentError => e
  e.message   # => "FieldStruct::Avro: Roster#logged is 2026-10-25T21:55:12.123456789Z, which has more precision than timestamp-micros; round it, or use timestamp: :nanos"
end


nanos = FieldStruct::Avro.encode(entry, timestamp: :nanos)
FieldStruct::Avro.decode(Roster, nanos, timestamp: :nanos) == entry   # => true
FieldStruct::Avro.to_datum(entry, timestamp: :nanos).keys             # => ["keeperName", "logged"]
```
 In the datum, the `serialize :avro` mapping renamed `keeper_name` to `keeperName`. `serialization:` defaults to `:avro`. Reading gets the same care. The `avro` gem matches fields on their base type alone, so a decimal read at a different scale would come out as a wrong number with no warning. The adapter compares the two schemas first and refuses the decode, listing every problem it found. 
```ruby
module Spring
  class Tide < FieldStruct::Base
    required :height, :big_decimal, round: 2
  end
end


module Autumn
  class Tide < FieldStruct::Base
    required :height, :big_decimal, round: 3
  end
end


logged = FieldStruct::Avro.encode(Spring::Tide.new(height: '4.25'))
written_with = FieldStruct::Avro.schema(Spring::Tide).merge('namespace' => 'Autumn')


begin
  FieldStruct::Avro.decode(Autumn::Tide, logged, writer_schema: written_with)
rescue ArgumentError => e
  e.message   # => "FieldStruct::Avro can't read these bytes: height: written as decimal (scale 2), read as decimal (scale 3). The avro gem would decode them as the wrong value, or fail; this is not a compatible schema change"
end
```
 Every error is an `ArgumentError` naming the class and field, and none of them echoes the value of a `sensitive: true` field. Bytes that can’t be read at all raise a single `ArgumentError`, with the `avro` gem’s own error as its `cause`. ## Options [Section titled “Options”](#options) A field’s `avro:` option is a Hash. With `type:` you replace the whole mapping by an Avro type of your own, and the other keys adjust the generated one. On array and union fields, every key except `type:` applies to the items. | Key | Meaning | | ---------------------- | ------------------------------------------------------------ | | `type:` | an Avro type (Hash or String) used as is | | `timestamp:` | `:micros`, `:nanos` or `:millis` for this field | | `precision:`, `scale:` | the decimal’s precision and scale | | `enum: false` | write a symbol field as `string` | | `enum_default:` | the symbol to read when the writer used one the reader lacks | 
```ruby
class Reading < FieldStruct::Base
  required :depth, :big_decimal, avro: { scale: 3, precision: 10 }
  required :taken, :time, avro: { timestamp: :millis }
  required :state, :symbol, enum: %i[calm rough], avro: { enum_default: :calm }
  required :station, :string, avro: { type: { 'type' => 'string', 'x-origin' => 'gauge' } }
end


types = FieldStruct::Avro.schema(Reading)['fields'].to_h { |f| [f['name'], f['type']] }
types['depth']    # => {"type"=>"bytes", "logicalType"=>"decimal", "precision"=>10, "scale"=>3}
types['taken']    # => {"type"=>"long", "logicalType"=>"timestamp-millis"}
types['state']    # => {"type"=>"enum", "name"=>"Reading_state", "symbols"=>["calm", "rough"], "default"=>"calm"}
types['station']  # => {"type"=>"string", "x-origin"=>"gauge"}
```
 Every module function accepts `serialization:`, and the ones that write or read times accept `timestamp:` as well. | Call | Returns | | ------------------------------------------------------------------ | ------------------------------------------ | | `schema(klass, serialization:, timestamp:)` | the record schema, a Hash with String keys | | `to_datum(struct, serialization:, timestamp:)` | the datum Hash | | `from_datum(klass, datum, serialization:)` | a struct | | `encode(struct, serialization:, timestamp:)` | Avro binary | | `decode(klass, bytes, writer_schema:, serialization:, timestamp:)` | a struct | | `clear_cache` | `nil` | ## Limits [Section titled “Limits”](#limits) * When the writer used a symbol that the reader’s `enum:` lacks, the read raises and names the field, unless that field sets `avro: {enum_default:}`. * A handful of errors come straight from the `avro` gem and may quote the value: a decimal past its precision, an integer past 64 bits, or a value that does not fit an `avro: {type:}` override. * Schemas are cached per class. The cache sees a new or redeclared field, but not an `avro:` Hash or `enum:` Array edited in place, so redeclare the field. Use `clear_cache` when code reloads. ## See also [Section titled “See also”](#see-also) * [Introspection reference](/adapters/introspection/) * [How adapters work](/adapters/how-adapters-work/) * [Dates, times and zones](/reference/field-struct/dates-and-times/)

# Avro native encoder

> An optional Rust encoder for field_struct-avro: the same Avro bytes, written about 2.6 times faster, with the pure Ruby path as the fallback.

`field_struct-avro-native` is an optional speed-up for [`FieldStruct::Avro.encode`](/adapters/avro/). It writes the same bytes as the pure Ruby path, from Rust, and anything it isn’t sure about goes back to Ruby. `field_struct-avro` never depends on it. 
```ruby
gem 'field_struct-avro-native'
```
 
```ruby
require 'field_struct/avro/native'
```
 Without that `require`, nothing changes. ## What it speeds up [Section titled “What it speeds up”](#what-it-speeds-up) `encode` builds a datum with `to_datum`, then hands it to the `avro` gem’s binary writer. The writer is most of the cost. It validates the whole datum first, then writes varints one byte at a time. The native gem replaces only that last step. It compiles each writer schema once into an encoding plan and walks the datum in Rust into a single buffer. The numbers below are in `benchmarks/BASELINE.md` (“Native avro encoder”), measured on Ruby 4.0.7 with YJIT, the Order-like struct from `field_struct-avro`’s benchmark: | Workload | Pure Ruby | Native | Speedup | | -------------------------------- | ----------------- | ----------------- | ------- | | `encode`, 1 order | 23,476 per second | 61,468 per second | 2.62x | | `encode`, 1000 orders (per call) | 23.2 | 61.6 | 2.66x | | Objects allocated per order | 417 | 155 | | The write step alone goes from 26.4 us to 1.9 us, about 14 times faster. What remains is mostly `to_datum`, at about 12.6 us. Reading is untouched: `decode` stays pure Ruby. ## Turn it on [Section titled “Turn it on”](#turn-it-on) Require it once, after `field_struct/avro`. `FieldStruct::Avro::Native.enabled?` tells you whether the encoder is in place. 
```ruby
require 'field_struct/avro'


defined?(FieldStruct::Avro::Native)   # => nil
```
 
```ruby
require 'field_struct/avro/native'


FieldStruct::Avro::Native.enabled?    # => true
```
 The require prepends a small module to `FieldStruct::Avro`. From then on, the calls you already make go through the plan: 
```ruby
module Signals
  class Dispatch < FieldStruct::Base
    required :id, :uuid
    required :lamp, :symbol, enum: %i[fixed flashing]
    required :swell, :big_decimal, round: 2
    required :sent, :time, zone: 'America/Denver'
    optional :channels, :array, of: :string
  end
end


dispatch = Signals::Dispatch.new(id: '3c5e7a10-92b4-4f6d-8e21-0a7d5b9c1e44', lamp: :flashing, swell: '2.75',
                                 sent: '2026-07-01T08:00:00', channels: %w[ch-16 ch-9])


bytes = FieldStruct::Avro.encode(dispatch)    # the same bytes as without the require
FieldStruct::Avro.decode(Signals::Dispatch, bytes) == dispatch   # => true
```
 Output is byte for byte what the pure path writes, for every datum the pure path accepts. `FieldStruct::Avro::Native.encode(schema, datum)` is the lower-level call. It takes a parsed `Avro::Schema` and a datum, and returns the bytes, or `nil` when it leaves the datum to Ruby. ## What falls back to pure Ruby [Section titled “What falls back to pure Ruby”](#what-falls-back-to-pure-ruby) The encoder never raises an error of its own. When it isn’t sure about a datum it returns `nil`, and the pure path then writes it or raises exactly the error the [Avro page](/adapters/avro/) describes. It falls back for: * a value of a class it doesn’t expect, such as an Integer in a `double` field or a `DateTime` in a `date` field * a value out of range: an integer past `int` or `long`, a decimal past its precision or scale, a time past `long` * a String in an encoding other than UTF-8 (7-bit US-ASCII and binary are fine) * a record datum that isn’t exactly what `to_datum` builds * a union member it can’t rule in or out the way the `avro` gem would * a schema shape it doesn’t cover: `fixed`, and logical types other than `decimal` (on bytes), `date`, `timestamp-millis`, `timestamp-micros`, `timestamp-nanos` and the identity ones like `uuid` It also copies two quirks of `avro` 1.12 by falling back. A decimal zero at scale 0 raises “Rounding necessary”, and a map with a key that isn’t valid UTF-8 raises when the map sits inside a union. A fallback costs the pure path plus the failed attempt. A schema it can’t cover is remembered, so that check isn’t repeated for each call. The plan lives on the parsed schema, so it follows the adapter’s cache. A rebuilt entry, or `FieldStruct::Avro.clear_cache`, means a new schema and a new plan. ## Install [Section titled “Install”](#install) Today `gem install field_struct-avro-native` compiles the Rust extension on your machine. You need a stable Rust toolchain and a C compiler. Precompiled gems are planned, so that installing needs no Rust. They will be built with `rb-sys` cross-compilation for `x86_64-linux`, `aarch64-linux` and `arm64-darwin`, and every other platform keeps the source gem as its fallback. The release workflow builds and smoke-tests them, but nothing has been published yet. ## Limits [Section titled “Limits”](#limits) * Only `encode` is faster. `decode`, `schema`, `to_datum` and `from_datum` are the same code as before. * Anything but an exact `String`, `Hash`, `Array`, `Time`, `Date` or `BigDecimal` falls back, subclasses included. * Ruby 3.3 or newer, and the same `avro` gem (1.12) that `field_struct-avro` uses. ## See also [Section titled “See also”](#see-also) * [Avro](/adapters/avro/) * [How adapters work](/adapters/how-adapters-work/)

# Build your own adapter

> Write a generator for a new format in about 60 lines on top of FieldStruct::Introspection, then test and package it.

Let’s write a small adapter that turns a struct into a TypeScript interface, in about 60 lines. The same steps work for any target - a docs table, a GraphQL type, a SQL definition - and the first-party adapters follow them too. ## 1. Look at what the walk gives you [Section titled “1. Look at what the walk gives you”](#1-look-at-what-the-walk-gives-you) `FieldStruct::Introspection.properties` lists a struct’s fields in order. Every property carries the external `key`, the `field` itself, and a `node` that says what kind of type it has. Here is a struct with one of each kind. 
```ruby
class Waypoint < FieldStruct::Base
  optional :label, :string
end


class Trek < FieldStruct::Base
  required :name, :string
  required :days, :integer, in: 1..30
  optional :waypoints, :array, of: Waypoint
  optional :tags, :array, of: :string
  optional :permit, :union, of: %i[integer string]
  optional :starts, :date
  serialize :json, days: 'dayCount'
end


properties = FieldStruct::Introspection.properties(Trek)
properties.map(&:key)   # => ["name", "dayCount", "waypoints", "tags", "permit", "starts"]
properties.map { |p| p.node.class.name.split('::').last }
# => ["ScalarNode", "ScalarNode", "ArrayNode", "ArrayNode", "UnionNode", "ScalarNode"]
properties[1].node.options   # => {in: 1..30}
properties[2].node.element.klass   # => Waypoint
properties[4].node.members.map { |m| m.type.class }.map { |c| c.name.split('::').last }   # => ["Integer", "String"]
```
 Nodes come in four kinds: scalar, array, union and struct. A struct node is a reference to the class and is never expanded, so nesting and recursion are yours to handle. The walk reports declarations and nothing else, which leaves what `required` means, what a missing value is and how types map up to your adapter. Every member is in the [introspection reference](/adapters/introspection/). ## 2. Write the adapter [Section titled “2. Write the adapter”](#2-write-the-adapter) The adapter is a single module function. It dispatches on the node class with `case`, since the node classes have no common base, and it matches scalar types by the node’s type class. type_script.rb 
```ruby
module TypeScript
  Types = FieldStruct::Types
  SCALARS = {
    Types::Integer => 'number', Types::Float => 'number', Types::Boolean => 'boolean',
    Types::BigDecimal => 'string', Types::Value => 'unknown'
  }.freeze


  # Returns the interface source for +klass+ and every struct it refers to.
  def self.generate(klass, serialization: :json)
    out = {}
    declare(klass, serialization, out)
    out.values.join("\n")
  end


  def self.declare(klass, serialization, out)
    name = klass.name.split('::').last
    return if out.key?(name)


    out[name] = nil # reserve the name first, so a recursive struct stops here
    lines = FieldStruct::Introspection.properties(klass, serialization: serialization).map do |prop|
      type = prop.field.options[:ts] || type_for(prop.node, serialization, out)
      optional = prop.field.required? ? '' : '?'
      "  #{prop.key}#{optional}: #{type}#{' | null' unless prop.field.required?};"
    end
    out.delete(name) # re-insert at the end, so nested interfaces come first
    out[name] = "interface #{name} {\n#{lines.join("\n")}\n}\n"
  end


  def self.type_for(node, serialization, out)
    case node
    when FieldStruct::Introspection::StructNode
      declare(node.klass, serialization, out)
      node.klass.name.split('::').last
    when FieldStruct::Introspection::ArrayNode
      "#{node.element ? type_for(node.element, serialization, out) : 'unknown'}[]"
    when FieldStruct::Introspection::UnionNode
      node.members.map { |member| type_for(member, serialization, out) }.uniq.join(' | ')
    else
      scalar(node)
    end
  end


  def self.scalar(node)
    return SCALARS.fetch(node.type.class) if SCALARS.key?(node.type.class)


    enum = node.options[:enum]
    enum ? enum.map { |value| "'#{value}'" }.join(' | ') : 'string'
  end
end
```
 A field turns into one line. An optional field gets `?` and `| null`, because `to_json` writes `null` for a missing value. A struct node declares its nested interface first and then refers to it by name. Dates, times, UUIDs and the rest of the string family fall through to `string`, which is what `to_json` writes for them. ## 3. Run it [Section titled “3. Run it”](#3-run-it) 
```ruby
TypeScript.generate(Trek) # => "interface Waypoint {\n  label?: string | null;\n}\n\ninterface Trek {\n  name: string;\n  dayCount: number;\n  waypoints?: Waypoint[] | null;\n  tags?: string[] | null;\n  permit?: number | string | null;\n  starts?: string | null;\n}\n"
```
 The key `dayCount` comes from the `serialize :json` mapping. Pass `serialization:` to get another format’s names. ## 4. Let fields override the mapping [Section titled “4. Let fields override the mapping”](#4-let-fields-override-the-mapping) The generator looks at `prop.field.options[:ts]` before anything else. Unknown options pass through a field declaration untouched, so a field can state what it wants and field_struct needs no change. 
```ruby
class Hut < FieldStruct::Base
  required :code, :string
  optional :season, :symbol, enum: %i[summer winter year_round]
  optional :places, :integer, ts: 'bigint'
end


TypeScript.generate(Hut) # => "interface Hut {\n  code: string;\n  season?: 'summer' | 'winter' | 'year_round' | null;\n  places?: bigint | null;\n}\n"
```
 A pass-through option belongs to the whole field. An array element can’t carry one, so an override covers the entire field. ## 5. Handle recursion and anonymous structs [Section titled “5. Handle recursion and anonymous structs”](#5-handle-recursion-and-anonymous-structs) A recursive struct would loop if the generator expanded nodes. Struct nodes are references, though, and the generator reserves the name before it walks the fields. 
```ruby
class Junction < FieldStruct::Base
  required :label, :string
  optional :branches, :array, of: Junction
end


TypeScript.generate(Junction) # => "interface Junction {\n  label: string;\n  branches?: Junction[] | null;\n}\n"
FieldStruct::Introspection.named?(Junction)                      # => true
FieldStruct::Introspection.named?(Class.new(FieldStruct::Base))  # => false
```
 `Introspection.named?` says whether a class can serve as a definition name. An anonymous class can’t, so a real adapter should either raise a clear error for it or inline it. ## 6. Test it [Section titled “6. Test it”](#6-test-it) Test the output as text, one struct per example, and test the claim you make about the data. Here the claim is that the interface lists exactly the keys `to_json` writes. 
```ruby
keys = Oj.load(Trek.new(name: 'Haute Route', days: 7).to_json).keys
declared = TypeScript.generate(Trek).scan(/^  (\w+)\??:/).flatten.drop(1)
declared == keys   # => true
```
 `declared` drops the first match, which is `label` from the nested `Waypoint`. In a spec that becomes `expect(declared).to eq(keys)`, with one example per type and one per override. ## 7. Package it as a gem [Section titled “7. Package it as a gem”](#7-package-it-as-a-gem) Copy the shape of the first-party adapters. field_struct-typescript.gemspec 
```ruby
Gem::Specification.new do |spec|
  spec.name = 'field_struct-typescript'
  spec.version = '1.0.0'
  spec.summary = 'TypeScript interfaces for field_struct classes'
  spec.required_ruby_version = '>= 3.3'
  spec.files = Dir['lib/**/*.rb', 'README.md', 'LICENSE.txt']
  spec.add_dependency 'field_struct', '>= 1.0.0.pre1', '< 2'
end
```
 * The entry point is `lib/field_struct/typescript.rb`, with an explicit `require_relative` per file. * Module functions come first. Add an opt-in `Methods` module only if people want `Klass.to_typescript`. * Requiring the gem must leave your users’ classes alone. * For anything you can’t map, raise `ArgumentError` naming the class and field, and don’t guess. * Depend on `field_struct` alone. Any third-party library your format needs becomes a dependency of your gem. ## See also [Section titled “See also”](#see-also) * [Introspection reference](/adapters/introspection/) * [How adapters work](/adapters/how-adapters-work/): why adapters are shaped this way * [JSON Schema](/adapters/json-schema/): a finished adapter to read

# How adapters work

> Why the adapters are separate gems on one shared walk, why they describe the JSON, and why they refuse to approximate.

This page covers why the adapters look the way they do. To use one, read that adapter’s page. To write one, go to [Build your own adapter](/adapters/build-your-own/). ## Why separate gems [Section titled “Why separate gems”](#why-separate-gems) Every adapter has its own version, changelog and release tag. Someone who wants Avro installs Avro, with no JSON Schema generator, Protobuf runtime or tracing library along for the ride, and a fix in one adapter never forces a release of another. The base gems stay small for the same reason. `field_struct` has no JSON Schema export and no `to_json_schema` method (FS-B140), and `actionable` never loads OpenTelemetry. Only the adapters that need a third-party library, like `avro` or `google-protobuf`, depend on it. The tools adapter depends on neither `mcp` nor `ruby_llm`. Each one is needed only by its own `require`, and a missing one raises an error that names the gem to add. The cost is more gems to install and keep in step. We think it is worth it, and the version ranges in each adapter’s gemspec do the keeping in step. ## Why one walk [Section titled “Why one walk”](#why-one-walk) JSON Schema, Avro and Protobuf all begin the same way: go through the fields, find each one’s external name, and see what kind of type it has. If every adapter read a struct’s internals on its own, each would lean on private details and each would hit its own bugs in the same spots. [`FieldStruct::Introspection`](/adapters/introspection/) is that first step, written once and living in `field_struct`. It reports declarations and nothing more. Nullability, defaults and type mapping differ by format, so it decides none of them. Avro writes `["null", T]` for an optional field, JSON Schema writes `"type": ["T", "null"]`, and Protobuf writes `optional`. Keeping the walk neutral lets each adapter be right about its own format. One side effect: anyone can write an adapter. Third-party exporters get the same walk as the first-party ones, and core has nothing else aimed at exporters. ## Why they describe the JSON [Section titled “Why they describe the JSON”](#why-they-describe-the-json) When a format forces a choice between Ruby behaviours, the adapters describe what a struct writes, not what it accepts. Setters are permissive - they take `'42'` for an integer and a Hash for a nested struct - while `to_json` is canonical. The JSON Schema adapter describes that canonical form (JS-I1), so the `to_json` of every valid instance validates and the schema stays short enough to read. It also explains why an optional field is nullable in JSON Schema: `to_json` writes `null` for each unset field. And a field with a default isn’t `required`, because the default fills in a missing key. ## Why never approximate [Section titled “Why never approximate”](#why-never-approximate) When an adapter can’t state a rule exactly, it raises or leaves the rule out. It never rounds, truncates or guesses. * Avro raises on a time with nanoseconds under a micros schema (AV-I1). Rounding would alter the value, and a silently altered value is the worst failure a data format can have. * Avro compares a pair of schemas before reading old bytes, because the `avro` gem would decode a decimal at the wrong scale into a wrong number without any error. * Protobuf never numbers fields by declaration order, since reordering a class would then change the wire format silently (PB-I1). It refuses a union too, because a `oneof` needs a number per member and there is no way to declare one yet. * JSON Schema omits `in:` on dates and `round:` on decimals, since it can’t express them. `pattern_for` returns `nil` unless its translation is exact (JS-I2), because a wrong pattern would make a validator in another language reject values the struct accepts. It also refuses a pattern that a backtracking JavaScript engine could take exponential time on, even though Ruby itself is safe, since those schemas get read by validators that handle untrusted input (JS-I3). Each case follows one rule: a clear error or a documented gap beats a value that is quietly wrong. The cost is that some structs can’t be exported until you make a choice, like giving every field a number. ## Why they don’t change your classes [Section titled “Why they don’t change your classes”](#why-they-dont-change-your-classes) Requiring an adapter adds a module and nothing more. After `require 'field_struct/avro'` your classes have no `to_avro` method. When you want `Hut.to_avro_schema`, include the adapter’s `Methods` module in the class. Everything also works as a module function, `FieldStruct::Avro.schema(Hut)`, with the class left alone (AV-I8). OpenTelemetry is the one exception. Tracing has to wrap `Action.run`, so requiring `actionable/otel` switches it on. It touches core in exactly two places, and results, history and exceptions come out unchanged (OT-I3, OT-I4). ## What an adapter may rely on [Section titled “What an adapter may rely on”](#what-an-adapter-may-rely-on) An adapter, whether first-party or yours, may rely on this public API, each item with a promise attached: * the `Introspection` members and the frozen shape of their nodes * the `Field` readers, the `Metadata#serialization` mapping, the type-class readers and the `ruby_type` table (FS-B155 to FS-B164) * the identity guarantees, so an adapter can cache per class and know exactly when to rebuild It may not rely on private methods, on `Types::Base` offering an export hook (core defines none, so an adapter asks with `respond_to?`), or on a pass-through option being validated. Options like `avro:` and `proto:` sit in `options` verbatim, and what they mean belongs to the adapter that reads them. ## Where we are not sure [Section titled “Where we are not sure”](#where-we-are-not-sure) The shared contract says an array of unions records only the union class, so you can’t reach the members of that union from the array node. It is documented, and the specs give no reason beyond how arrays store their element type. If you run into it, override the array field with the adapter’s own option. ## See also [Section titled “See also”](#see-also) * [Introspection reference](/adapters/introspection/) * [Build your own adapter](/adapters/build-your-own/) * [Adapters overview](/adapters/)

# Introspection reference

> The format-neutral walk of a struct's fields that every adapter is built on: properties, node kinds, options and stability promises.

`FieldStruct::Introspection` walks a struct’s fields without changing anything, for code that exports a struct to another format. The JSON Schema, Avro and Protobuf adapters sit on top of it, and any adapter you write can too. It ships inside `field_struct` and loads with `require 'field_struct'` (FS §4.12, FS-B140 to FS-B152). The walk reports declarations and nothing else. The adapter decides what `null` means for an optional field, which defaults to write, how types map and what a pass-through option does (FS-B151). 
```ruby
class Waypoint < FieldStruct::Base
  optional :label, :string
end


class Route < FieldStruct::Base
  required :name, :string
  optional :waypoints, :array, of: Waypoint
  serialize :json, waypoints: 'stops'
end


name, stops = FieldStruct::Introspection.properties(Route)
name.key                               # => "name"
name.field.required?                   # => true
stops.key                              # => "stops"
stops.node.element.klass == Waypoint   # => true
```
 ## `properties` [Section titled “properties”](#properties) 
```ruby
Introspection.properties(klass, serialization: :json) # => Array<Property>
```
 You get one `Property` for each field of `klass`, in declaration order and with inherited fields included. A struct without fields gives `[]`. `serialization` is a Symbol or String that selects which `serialize` mapping names the keys, and a format nobody declared keeps every field name (FS-B141, FS-B142). Every call returns a fresh array of fresh objects, and nothing is cached on the class. 
```ruby
FieldStruct::Introspection.properties(Route).map(&:key)                          # => ["name", "stops"]
FieldStruct::Introspection.properties(Route, serialization: :csv).map(&:key)     # => ["name", "waypoints"]
FieldStruct::Introspection.properties(Class.new(FieldStruct::Base))              # => []
FieldStruct::Introspection.properties(Route).first.equal?(FieldStruct::Introspection.properties(Route).first)   # => false
```
 ## `Property` [Section titled “Property”](#property) | Reader | Returns | | ------- | ------------------------------------------------------------------------------------------------ | | `field` | the class’s own `FieldStruct::Field`, not a copy | | `key` | the external name for the chosen format, always a String | | `node` | the node for the field’s type, built by `Introspection.node(field.type_instance, field.options)` | `Field` has public readers an adapter may rely on (FS-B155): `name` (a Symbol), `type` (the resolved type class), `type_instance` (one per field), `required?`, `sensitive?`, `description`, `default`, `options`, `coercion_policy` and `rbs_type`. `Field#default` is the raw declared default: a value or a callable, never called by the reader. `nil` means no default. A default of `false`, `0`, `''` or `[]` is a real default (FS-B156). ## Node kinds [Section titled “Node kinds”](#node-kinds) `node(type, options = {})` picks a node class from the type instance. There are exactly four, with no shared base class, so dispatch with `case` (FS-B143). | Node | Built for | Readers | | ------------ | ---------------------------------------------------------------------------- | ---------------------------- | | `ScalarNode` | every other type: `:string`, `:integer`, `:value`, custom types and the rest | `type`, `options` | | `ArrayNode` | `Types::Array` | `type`, `options`, `element` | | `UnionNode` | `Types::Union` | `type`, `members` | | `StructNode` | `Types::Nested` | `type`, `klass` | 
```ruby
class Leg < FieldStruct::Base
  required :nights, :integer, in: 1..5
  optional :tags, :array, of: :string, element: { strict: true }
  optional :ref, :union, of: %i[integer string]
  optional :stop, Waypoint
end


nights, tags, ref, stop = FieldStruct::Introspection.properties(Leg).map(&:node)


[nights, tags, ref, stop].map { |node| node.class.name.split('::').last }
# => ["ScalarNode", "ArrayNode", "UnionNode", "StructNode"]
nights.options                        # => {in: 1..5}
tags.element.options                  # => {strict: true}
ref.members.map { |member| member.type.ruby_type }   # => [Integer, String]
stop.klass                            # => Waypoint
```
 ### Scalar nodes [Section titled “Scalar nodes”](#scalar-nodes) `type` is the field’s own type instance. `options` is the Hash the value is checked against, which for a field is `Field#options` itself (FS-B144). ### Array nodes [Section titled “Array nodes”](#array-nodes) `options` is whatever the array was declared with, so it holds `of_type:` and, when given, `element:`. It is `{}` if the array is an element of another array or a member of a union. `element` is built on first read and the same value comes back afterwards, so an adapter that overrides the array at field level never pays for the element. It is: * a `ScalarNode` for `of: :string`, built with the `element:` options, or `{}` * a `StructNode` for `of: Waypoint` * `nil` when the element type is unknown or is a union. An array of unions records only the union class, so its members can’t be reached from the array node * for `of: :array`, an `ArrayNode` whose own `element` is `nil`, so an array of arrays has exactly two levels 
```ruby
class Timetable < FieldStruct::Base
  optional :days, :array, of: :array
  optional :slots, :array, of: :union
end


days, slots = FieldStruct::Introspection.properties(Timetable).map(&:node)
days.element.class.name.split('::').last   # => "ArrayNode"
days.element.element                        # => nil
slots.element                               # => nil
```
 ### Union nodes [Section titled “Union nodes”](#union-nodes) `members` is a frozen Array holding one node per member in declared order. A member carries no options, so each node is built with an empty Hash (FS-B147). ### Struct nodes [Section titled “Struct nodes”](#struct-nodes) `klass` is a reference and is never expanded, so the walk doesn’t recurse into a struct’s own properties. Call `properties(node.klass)` yourself, and use `named?` plus a definitions table to cut off self-referential structs. The walk itself can’t loop (FS-B148). ## `node` [Section titled “node”](#node) 
```ruby
Introspection.node(type, options = {}) # => ScalarNode | ArrayNode | UnionNode | StructNode
```
 `node` builds a node for a type instance and the options Hash it is checked with. Anything that isn’t an array, union or nested type becomes a `ScalarNode`, a non-type passed by mistake included. 
```ruby
count = FieldStruct::Introspection.node(FieldStruct::Types::Integer.new, in: 1..3)
count.class.name.split('::').last   # => "ScalarNode"
count.options                       # => {in: 1..3}
```
 ## `named?` [Section titled “named?”](#named) 
```ruby
Introspection.named?(klass) # => Boolean
```
 True when the class has a name usable as a definition key or title. An anonymous class gives false, and so does a class under an anonymous module, whose name looks like `#<Module:0x...>::Addr`. A class in an ordinary namespace gives true (FS-B150). 
```ruby
module Alpine
  class Refuge < FieldStruct::Base; end
end


FieldStruct::Introspection.named?(Alpine::Refuge)                   # => true
FieldStruct::Introspection.named?(Class.new(FieldStruct::Base))     # => false
```
 ## What `options` holds [Section titled “What options holds”](#what-options-holds) Adapters read `Field#options` through the nodes, and these are the promises (FS-B157): * `enum:` and `in:` are as declared: an Array of Strings or Symbols, a Range or an Array. * `round:`, `base:` and `strict:` are as declared, and `round:` and `values:` are present only when declared. * `format:` on a string-family field is a Regexp, the declared one or the type’s default. * `format:` on a date or time field is the declared value: `nil` when none was given (the key is present), a preset Symbol such as `:iso8601`, or a String. It is never a resolved object. * `zone:` is as written. * `values:` on `:boolean` is the resolved Hash `{truthy: [...], falsy: [...]}`. * Pass-through options such as `avro:`, `proto:` and `json_schema:`, and any unknown key, are present verbatim and never validated. * An element’s options are validated like a scalar field’s, so a pass-through option on an `element:` raises at declaration. Pass-through options are for whole fields only (FS-B162). 
```ruby
class Climb < FieldStruct::Base
  required :gain, :float, round: 1, in: 0.0..99.9, unit: 'km'
  optional :logged, :date
end


gain, logged = FieldStruct::Introspection.properties(Climb).map(&:node)
gain.options      # => {round: 1, in: 0.0..99.9, unit: "km"}
logged.options    # => {format: nil}
```
 ## Stability promises [Section titled “Stability promises”](#stability-promises) * Every `Property` and every node is frozen. The `options` Hashes belong to the struct and are frozen shallowly at most, so treat what they hold (an `enum:` Array, a `values:` Hash) as read-only (FS-B149). * `Introspection` mutates nothing and caches nothing on the class, and calling it never changes how a struct behaves. A field redeclared after a call is a new `Field` that the next call picks up (FS-B152). * `Metadata#serialization(format)` returns the same frozen Hash until the class redeclares that format, and `Metadata#each` yields the same `Field` objects while a field stays unchanged. A cache keyed on those objects holds exactly until the class’s declarations change (FS-B159). * Core ships no exporter: there is no `FieldStruct::JSONSchema`, no `to_json_schema`, and no format named other than `:json` (FS-B140). ## Type readers [Section titled “Type readers”](#type-readers) An adapter that maps types reads them off `type_instance` (FS-B163, FS-B164). * `ruby_type` is `Integer` for `:integer`, `Float`, `String` for the whole string family, `[TrueClass, FalseClass]` for `:boolean`, `Symbol`, `Date`, `Time`, `DateTime`, `BigDecimal`, `Object` for `:value`, `Array`, the struct class for a nested field, and the flat list of member classes for a union. * `default_format` exists on `:uuid`, `:url`, `:email` (a Regexp) and on the date and time types (`nil`). `default_round` exists on `:float` and `:big_decimal`. Ask with `respond_to?` first, since other types don’t define them. * `Types::Union#member_types` gives the member type instances, and `Types::Nested#struct_class` gives the class. * An optional hook on a custom type, like `json_schema`, is the adapter’s convention and not core’s. Check `respond_to?` on the instance and never assume the hook exists (FS-B161). ## See also [Section titled “See also”](#see-also) * [Build your own adapter](/adapters/build-your-own/) * [How adapters work](/adapters/how-adapters-work/) * [Introspection and tooling](/reference/field-struct/introspection-and-tooling/)

# JSON Schema

> Turn the JSON a struct writes into a JSON Schema, for API docs, validators in other services and tool parameters.

`field_struct-json_schema` takes the JSON a struct writes with `to_json` and reads with `from_json`, and describes it as a JSON Schema (draft 2020-12). It does not validate anything itself. The schema goes to whatever validator, documentation tool or code generator you already run. 
```ruby
gem 'field_struct-json_schema'
```
 
```ruby
require 'field_struct/json_schema'
```
 Requiring it adds `FieldStruct::JSONSchema` and nothing more. Your own classes stay as they were until you opt in (see [How adapters work](/adapters/how-adapters-work/)). ## The schema of a struct [Section titled “The schema of a struct”](#the-schema-of-a-struct) `FieldStruct::JSONSchema.generate` takes a struct class and hands back a Hash with String keys. 
```ruby
require 'field_struct/json_schema'


class CatalogCard < FieldStruct::Base
  required :title, :string
  required :shelfmark, :string, format: /\A\d{6}\z/
  optional :folios, :integer, in: 1..900
  optional :tier, :symbol, enum: %i[open sealed]
  optional :keywords, :array, of: :string
  serialize :json, folios: 'folioCount'
end


schema = FieldStruct::JSONSchema.generate(CatalogCard)
schema['title']                      # => "CatalogCard"
schema['required']                   # => ["title", "shelfmark"]
schema['properties'].keys            # => ["title", "shelfmark", "folioCount", "tier", "keywords"]
schema['properties']['shelfmark']    # => {"type"=>"string", "pattern"=>"^\\d{6}$"}
schema['properties']['folioCount']   # => {"type"=>["integer", "null"], "minimum"=>1, "maximum"=>900}
```
 Property names follow what `to_json` writes, which is why `folios` appears as `folioCount`. A field is `required` in the schema when it is required and has no default, since a default fills in a missing key. Optional fields also accept `null`. Each `generate` call returns a fresh copy, so editing one result never touches another. If you want `CatalogCard.to_json_schema` as a class method, include the opt-in module. 
```ruby
class Curator < FieldStruct::Base
  include FieldStruct::JSONSchema::Methods


  required :surname, :string
end


Curator.to_json_schema == FieldStruct::JSONSchema.generate(Curator)   # => true
```
 ## Use case: validate a payload in another service [Section titled “Use case: validate a payload in another service”](#use-case-validate-a-payload-in-another-service) Say a second service receives what the archive app sends and wants to turn away bad payloads before its own code sees them. Publish the schema as a file and let that service load it into its validator. The validator below is `json_schemer`, a separate gem that this adapter does not depend on. 
```ruby
require 'json_schemer'


validator = JSONSchemer.schema(schema)


good = JSON.parse(CatalogCard.new(title: 'Tide tables', shelfmark: '204117', folios: 88).to_json)
good                    # => {"title"=>"Tide tables", "shelfmark"=>"204117", "folioCount"=>88, "tier"=>nil, "keywords"=>nil}
validator.valid?(good)  # => true


bad = { 'title' => 'Tide tables', 'shelfmark' => 'A12' }
validator.valid?(bad)   # => false
validator.validate(bad).map { |error| error['error'] }   # => ["string at `/shelfmark` does not match pattern: ^\\d{6}$"]
```
 For canonical JSON the schema is exact: it accepts what the struct accepts and rejects what the struct rejects. The `to_json` of any valid instance passes. ## Use case: API documentation and nested structs [Section titled “Use case: API documentation and nested structs”](#use-case-api-documentation-and-nested-structs) A nested struct is written once under `$defs` and referenced by name. The root class is referenced as `#`, so a recursive struct works. An anonymous struct is inlined. 
```ruby
class Annotation < FieldStruct::Base
  required :rating, :integer, in: 1..5
  optional :remark, :string
end


class Exhibit < FieldStruct::Base
  required :name, :string
  optional :annotations, :array, of: Annotation
  optional :companion, Exhibit
end


exhibit = FieldStruct::JSONSchema.generate(Exhibit)
exhibit['$defs'].keys                            # => ["Annotation"]
exhibit['properties']['annotations']['items']    # => {"anyOf"=>[{"$ref"=>"#/$defs/Annotation"}, {"type"=>"null"}]}
exhibit['properties']['companion']               # => {"anyOf"=>[{"$ref"=>"#"}, {"type"=>"null"}]}
```
 A field’s `description:` turns into the schema’s `description`, and a default that `to_json` would write turns into `default`. A sensitive field is tagged `x-sensitive`, and its default stays out. 
```ruby
class AccessGrant < FieldStruct::Base
  required :reader, :email, description: 'Address that receives the grant'
  optional :tier, :string, enum: %w[public staff], default: 'public'
  required :vault_code, :string, sensitive: true, default: 'hush'
end


props = FieldStruct::JSONSchema.generate(AccessGrant)['properties']
props['reader']['description']   # => "Address that receives the grant"
props['tier']['default']         # => "public"
props['vault_code']              # => {"x-sensitive"=>true, "type"=>"string"}
```
 ## Use case: an action’s input as tool parameters [Section titled “Use case: an action’s input as tool parameters”](#use-case-an-actions-input-as-tool-parameters) An action’s `input` block defines a struct, so its schema is a single call away. That schema is what a model needs in order to call the action as a tool. The [tools adapter](/adapters/tools/) wraps this up for you, safety rules included. 
```ruby
class SearchCards < Actionable::Action
  input do
    required :phrase, :string
    optional :max_hits, :integer, in: 1..50
  end
end


params = FieldStruct::JSONSchema.generate(SearchCards.input_schema)
params['properties'].keys   # => ["phrase", "max_hits"]
params['required']          # => ["phrase"]
```
 ## Overrides [Section titled “Overrides”](#overrides) The `json_schema:` option on a field replaces the derived schema. It accepts a Hash, `true` (no constraint) or `false` (nothing validates). A custom type can define a `json_schema` method to the same end, and a type with neither comes out unconstrained and tagged `x-ruby-type`. 
```ruby
class Drawer < FieldStruct::Base
  required :label, :string, json_schema: { 'type' => 'string', 'minLength' => 4 }
  optional :contents, :value, json_schema: false
end


FieldStruct::JSONSchema.generate(Drawer)['properties']['label']   # => {"type"=>"string", "minLength"=>4}
```
 A bad override raises `ArgumentError` and names the class and field. ## Regexps with `pattern_for` [Section titled “Regexps with pattern_for”](#regexps-with-pattern_for) Ruby and JavaScript do not treat Regexps the same way. `FieldStruct::JSONSchema.pattern_for` translates a Ruby Regexp into an ECMA-262 pattern that matches exactly the same strings, or returns `nil`. Close enough is never good enough here, so any doubt means `nil`. 
```ruby
FieldStruct::JSONSchema.pattern_for(/\A\d+-\d+\z/)    # => "^\\d+-\\d+$"
FieldStruct::JSONSchema.pattern_for(/\bnote\b/)       # => nil
FieldStruct::JSONSchema.pattern_for(/\A(x+)+\z/)      # => nil
```
 The last Regexp has an exact translation, but a backtracking JavaScript engine could spend exponential time on it, so the adapter refuses. In a struct, a `format:` Regexp that can’t be translated becomes `x-ruby-pattern`, an annotation that no validator checks. 
```ruby
class Crate < FieldStruct::Base
  required :tag, :string, format: /\A[A-Z]{2}-\d{5}\z/
  required :donor, :string, format: /\A\p{L}+\z/
end


props = FieldStruct::JSONSchema.generate(Crate)['properties']
props['tag']     # => {"type"=>"string", "pattern"=>"^[A-Z]{2}-\\d{5}$"}
props['donor']   # => {"type"=>"string", "x-ruby-pattern"=>"\\A\\p{L}+\\z"}
```
 ## Options [Section titled “Options”](#options) | Option | On | Meaning | | ---------------- | ---------- | --------------------------------------------------------------- | | `serialization:` | `generate` | which `serialize` mapping names the properties; default `:json` | | `json_schema:` | a field | a Hash, `true` or `false` that replaces the derived schema | | `description:` | a field | becomes `description` | | `sensitive:` | a field | adds `x-sensitive` and hides the default | `FieldStruct::JSONSchema.clear_cache` empties the per-class cache. That cache keeps classes alive, so call it whenever code reloads. ## Limits [Section titled “Limits”](#limits) When JSON Schema has no way to say a rule, the adapter leaves it out. It never approximates. * `in:` on dates, times and decimals, and `strict:`, `base:` and `round:`, do not reach the schema. The struct still enforces them. * A decimal shows up as a string matching a decimal pattern, because `to_json` writes it as a string. * `format:` on a date or time becomes `format` only for the default or `:iso8601` form. * An optional string field with `enum:` or `format:` accepts a blank string too, since the struct reads a blank string as missing. * `unknown_attributes :raise` on a struct adds `additionalProperties: false`. * The cache notices a new or redeclared field, but not an `enum:` Array edited in place. Redeclare the field instead. ## See also [Section titled “See also”](#see-also) * [Actions as LLM and MCP tools](/adapters/tools/) * [How adapters work](/adapters/how-adapters-work/) * [Adapters overview](/adapters/)

# OpenTelemetry

> Give each action run a span, and each step a child span, that carry the outcome and the code but never a value.

With `actionable-otel`, each `.run` opens a span and each step or hook that executes opens a child span. The outcome and the result code go on as attributes, and a declared failure flags its span as an error. Input values and output values are never recorded. 
```ruby
gem 'actionable-otel'
gem 'opentelemetry-sdk'
gem 'opentelemetry-exporter-otlp'
```
 The gem depends on `opentelemetry-api` alone. Which SDK and exporter to use is up to your application. Caution This adapter differs from the others: `require 'actionable/otel'` changes behaviour by switching tracing on for every action. The core gem never loads OpenTelemetry by itself. 
```ruby
require 'opentelemetry/sdk'
require 'actionable/otel'


OpenTelemetry::SDK.configure { |c| c.service_name = 'apiary-rounds' }
```
 ## What a run looks like [Section titled “What a run looks like”](#what-a-run-looks-like) To see all of it, we need an action with three steps plus a success hook, a failure hook and an `always` hook. Spans here go to the SDK’s in-memory exporter so we can read them back. A real app would point the OTLP exporter at a collector. 
```ruby
require 'opentelemetry/sdk'
require 'actionable/otel'


exporter = OpenTelemetry::SDK::Trace::Export::InMemorySpanExporter.new
OpenTelemetry::SDK.configure do |c|
  c.add_span_processor(OpenTelemetry::SDK::Trace::Export::SimpleSpanProcessor.new(exporter))
end


class ColonyRound < Actionable::Action
  fails :swarmed


  step :lift_lid
  step :tally_brood
  step :seal_up
  on_success :log_honey
  on_failure :flag_for_split
  always :stamp_ledger


  private


  def lift_lid = @lid_up = true
  def tally_brood = fail!(:swarmed)
  def seal_up = @sealed = true
  def log_honey = @logged = true
  def flag_for_split = @flagged = true
  def stamp_ledger = @stamped = true
end


ColonyRound.run.code   # => :swarmed


spans = exporter.finished_spans
# the run span closes last, so it is last
spans.last.name                                          # => "ColonyRound.run"
spans.last.attributes['actionable.outcome']              # => "failure"
spans.last.attributes['actionable.code']                 # => "swarmed"
spans.last.status.description                            # => "swarmed"
```
 A tracing backend would draw that run like this: 
```plaintext
ColonyRound.run              outcome=failure code=swarmed  status=ERROR(swarmed)
  ColonyRound/lift_lid       section=main
  ColonyRound/tally_brood    section=main code=swarmed
  ColonyRound/flag_for_split section=failure
  ColonyRound/stamp_ledger   section=always
```
 `seal_up` has no span because it never ran: `fail!` stopped the main steps first. The failure hook ran where the success hook would have, and `always` runs either way. A run that succeeds has no error status. 
```ruby
spans.map(&:name)   # => ["ColonyRound/lift_lid", "ColonyRound/tally_brood", "ColonyRound/flag_for_split", "ColonyRound/stamp_ledger", "ColonyRound.run"]
spans[1].attributes['actionable.code']        # => "swarmed"
spans[2].attributes['actionable.section']     # => "failure"
spans[0].attributes['actionable.step.kind']   # => "method"
```
 ## Spans and attributes [Section titled “Spans and attributes”](#spans-and-attributes) | Span | Name | Attributes | | ------------ | ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | | run | `<Class>.run` | `actionable.action`, then `actionable.outcome` (`success`, `failure`, `skipped`) and `actionable.code` when the run returns | | step or hook | `<Class>/<name>` | `actionable.action`, `actionable.step`, `actionable.step.kind` (`method`, `action`, `case`), `actionable.section` (`main`, `success`, `failure`, `skip`, `always`), and `actionable.code` when the step recorded a result | * An anonymous action carries the label `Actionable::Action`. * A step that runs a nested action takes the child class’s name, and the child’s run span sits beneath it. * A case step is a single span, with the chosen branch running inside it. * A step held back by an `if:` or `unless:` guard gets no span. * A skip is not an error, but a declared failure is, so it counts toward your error rate. To tell declared failures from exceptions, filter on `actionable.code`. The action’s `measure` mode has no effect on spans, and sampling belongs to the SDK. A run stubbed through the `actionable/rspec` stubs emits no span. ## What is never recorded [Section titled “What is never recorded”](#what-is-never-recorded) A span never sees input fields, output fields, messages, error text or metadata. Everything named in a span is a class, a step, a section, an outcome or a result code. Codes go in exactly as written, so keep them fixed. Something like `fail!(:"rejected_#{reason}")` would put a changing value into every trace and inflate the count of distinct attribute values. When you need an attribute of your own, set it on the current span from inside a step. ## Exceptions [Section titled “Exceptions”](#exceptions) When an exception escapes a run, it is recorded once, on the run span, and then raised again as it was. The event holds only the exception class by default, since messages and backtraces can contain input values. A declared failure counts as a normal result and adds no exception event. 
```ruby
class Collapse < Actionable::Action
  step :crack_frame


  private


  def crack_frame = raise('tag fr_4411 cracked')
end


exporter.reset
begin
  Collapse.run
rescue RuntimeError => e
  e.message   # => "tag fr_4411 cracked"
end


event = exporter.finished_spans.last.events.first
event.name         # => "exception"
event.attributes   # => {"exception.type" => "RuntimeError"}
```
 The trace never got the message, though the application still did. ## Settings [Section titled “Settings”](#settings) Both settings are process-wide, so set them once at boot. | Setting | Default | Meaning | | -------------------------------------------- | ------------ | ------------------------------------------------ | | `Actionable::Otel.step_spans = false` | `true` | emit run spans only, no step or hook spans | | `Actionable::Otel.exception_details = :full` | `:type_only` | also record the exception message and stacktrace | 
```ruby
Actionable::Otel.step_spans?          # => true
Actionable::Otel.step_spans = false
Actionable::Otel.step_spans?          # => false
Actionable::Otel.step_spans = true


Actionable::Otel.exception_details    # => :type_only


begin
  Actionable::Otel.exception_details = :message
rescue ArgumentError => e
  e.message   # => "Actionable::Otel.exception_details must be :type_only or :full, got :message"
end
```
 ## Cost and volume [Section titled “Cost and volume”](#cost-and-volume) A run costs one span, and every step or hook that executes costs one more. With no SDK installed, OpenTelemetry’s no-op provider swallows the spans and the overhead stays small. The provider is looked up when a run starts, so one installed after `actionable/otel` loaded takes effect on the next run. If volume gets too high, set `step_spans = false` or sample in the SDK. ## Compatibility [Section titled “Compatibility”](#compatibility) You need Ruby 3.3 or newer, `actionable-rb` 2.x and `opentelemetry-api` 1.7 or newer. The adapter wraps `Action.run` and one internal method of the runner, so a new major of `actionable-rb` may call for a new release here. ## See also [Section titled “See also”](#see-also) * [Hooks and history](/reference/actionable/hooks-and-history/): the sections that become `actionable.section` * [Declared outcomes](/reference/actionable/declared-outcomes/) * [How adapters work](/adapters/how-adapters-work/)

# Protobuf

> Print a struct as .proto source, build its message class, and move instances to and from bytes, using field numbers you pick.

Preview `field_struct-protobuf` sits at `1.0.0.pre1`. Its spec settles the behaviour, though no release has gone out yet. `field_struct-protobuf` gives a struct a Protocol Buffers form without a `protoc` run. It prints `.proto` source for other teams, registers a message class with `google-protobuf`, and converts instances to messages, to binary and back. 
```ruby
gem 'field_struct-protobuf'
```
 
```ruby
require 'field_struct/protobuf'
```
 You choose the field numbers. Each field carries `proto: {number: n}` and the gem never guesses one. If it numbered by declaration order, moving two lines around in a class would quietly change the wire format. ## The schema of a struct [Section titled “The schema of a struct”](#the-schema-of-a-struct) `FieldStruct::Protobuf.proto` prints the file for a single class. It prints from the descriptor that gets registered, so the text and the registered message can’t drift apart. 
```ruby
require 'field_struct/protobuf'


module Fleet
  class Depot < FieldStruct::Base
    required :name, :string, proto: { number: 1 }
  end


  class Trip < FieldStruct::Base
    required :route, :string, proto: { number: 1 }
    optional :meters, :integer, proto: { number: 2 }
    optional :origin, Depot, proto: { number: 3 }
    optional :waypoints, :array, of: :string, proto: { number: 4 }
    optional :battery, :big_decimal, proto: { number: 5 }
    optional :departed, :time, zone: 'America/Denver', proto: { number: 6 }
  end
end


text = FieldStruct::Protobuf.proto(Fleet::Trip)
text.lines.grep(/\A(message|  )/).map(&:strip)
# => ["message Trip {", "optional string route = 1;", "optional int64 meters = 2;", ".fleet.Depot origin = 3;", "repeated string waypoints = 4;", "optional string battery = 5;", ".google.protobuf.Timestamp departed = 6;", "}"]
FieldStruct::Protobuf.file_name(Fleet::Trip)   # => "field_struct/fleet/trip.proto"
FieldStruct::Protobuf.full_name(Fleet::Trip)   # => ".fleet.Trip"
```
 Here is the whole file for `Fleet::Trip`: 
```proto
// field_struct/fleet/trip.proto: generated by field_struct-protobuf from Fleet::Trip.
// Field numbers come from each field's proto: {number:} option.


syntax = "proto3";


package fleet;


import "field_struct/fleet/depot.proto";
import "google/protobuf/timestamp.proto";


message Trip {
  optional string route = 1;
  optional int64 meters = 2;
  .fleet.Depot origin = 3;
  repeated string waypoints = 4;
  optional string battery = 5;
  .google.protobuf.Timestamp departed = 6;
}
```
 The module `Fleet` turns into the package. Each class gets its own file with one message in it. A file imports the files of whatever structs it refers to. A struct can refer to itself, but two structs can’t point at each other. ## Type mapping [Section titled “Type mapping”](#type-mapping) | FieldStruct type | Protobuf | | -------------------------------------------------------------------- | ---------------------------------------------------------------------- | | `:binary` | `bytes` | | `:string`, `:immutable_string`, `:uuid`, `:email`, `:url`, `:symbol` | `string` | | `:big_decimal`, `:decimal` | `string`, so `19.9` stays exact | | `:date` | `string`, as `2026-11-01` | | `:boolean` | `bool` | | `:integer` | `int64` | | `:float` | `double` | | `:time`, `:datetime` | `.google.protobuf.Timestamp`; the `zone:` offset is restored on decode | | `:value` | `.google.protobuf.Value`; numbers come back as Floats | | a struct class | its message | | `:array, of: X` | `repeated` X | Singular scalars are all `optional`, so presence is explicit: a field nobody set reads back as `nil`, not `0` or an empty string. Arrays differ. Empty and unset look the same on the wire, so an unset array reads back as `[]`. ## Use case: encode and decode [Section titled “Use case: encode and decode”](#use-case-encode-and-decode) Take a trip that starts at the north depot and carries a battery reading. 
```ruby
trip = Fleet::Trip.new(route: 'Riverside loop', meters: '5400', origin: { name: 'North depot' },
                       waypoints: %w[dock-12 dock-31], battery: '87.5', departed: Time.utc(2026, 10, 27, 15, 30))


bytes = FieldStruct::Protobuf.encode(trip)
bytes.encoding   # => #<Encoding:BINARY (ASCII-8BIT)>


back = FieldStruct::Protobuf.decode(Fleet::Trip, bytes)
back == trip                         # => true
back.battery == BigDecimal("87.5")   # => true
back.departed.utc_offset             # => -21600
back.origin.name                     # => "North depot"
```
 Code that `protoc` generates from the printed `.proto` can read these bytes. The adapter’s own specs prove it by compiling the text with `protoc`, so this page relies on that claim and does not run it. ## Use case: messages [Section titled “Use case: messages”](#use-case-messages) `message_class` builds the message for a class one time and registers it in `google-protobuf`’s generated pool. `to_message` and `from_message` convert a single instance. 
```ruby
depot = Fleet::Depot.new(name: 'Harbour depot')


message = FieldStruct::Protobuf.to_message(depot)
message.name                                                            # => "Harbour depot"
FieldStruct::Protobuf.message_class(Fleet::Depot).equal?(message.class)   # => true
FieldStruct::Protobuf.from_message(Fleet::Depot, message) == depot      # => true
```
 Message field names are the `serialize :protobuf` names, as given. Pass `serialization:` when you want the names of another format. ## Unset stays unset [Section titled “Unset stays unset”](#unset-stays-unset) 
```ruby
sparse = Fleet::Trip.new(route: 'Riverside loop')
message = FieldStruct::Protobuf.to_message(sparse)


message.has_meters?   # => false
FieldStruct::Protobuf.decode(Fleet::Trip, FieldStruct::Protobuf.encode(sparse)).meters      # => nil
FieldStruct::Protobuf.decode(Fleet::Trip, FieldStruct::Protobuf.encode(sparse)).waypoints   # => []
```
 ## It raises rather than guess [Section titled “It raises rather than guess”](#it-raises-rather-than-guess) When there is no exact mapping, the call raises `ArgumentError` and names the class and field. Cases are a field with no number, a number used twice, a union, an array of arrays and a custom type. 
```ruby
class Unnumbered < FieldStruct::Base
  required :dock, :string
end


class Twice < FieldStruct::Base
  required :dock, :string, proto: { number: 2 }
  required :slot, :string, proto: { number: 2 }
end


class Either < FieldStruct::Base
  required :dock, :union, of: %i[integer string], proto: { number: 1 }
end


[Unnumbered, Twice, Either].map do |klass|
  FieldStruct::Protobuf.proto(klass)
rescue ArgumentError => e
  e.message
end
# => ["Unnumbered: give every field a protobuf field number, e.g. `proto: {number: 1}`; missing on dock", "Twice: field numbers 2 are used twice", "Either#dock is a union, which field_struct-protobuf can't map yet"]
```
 ## Module functions [Section titled “Module functions”](#module-functions) | Call | Returns | | ------------------------------------------------------------------------------- | --------------------------------------- | | `proto(klass)` | the `.proto` text | | `file_name(klass)`, `full_name(klass)`, `package(klass)`, `message_name(klass)` | the names given to the file and message | | `file_descriptor(klass)` | the registered descriptor | | `message_class(klass)` | the `google-protobuf` message class | | `to_message(struct)`, `from_message(klass, message)` | one instance, to a message and back | | `encode(struct)`, `decode(klass, bytes)` | binary | ## Limits [Section titled “Limits”](#limits) * Output is proto3 only. There is no `oneof`, enum, map, service or option. * Registration lasts for the process and cannot be undone. If a class gains a field after its message was built, nothing notices, and the stale message rejects the new field. Reloading code means restarting. * Each class registers under one `serialization:`. Asking for a second one raises. * For malformed bytes, `decode` lets `Google::Protobuf::ParseError` pass through. * An integer past 64 bits raises `RangeError`. * `format:` and `in:` are not checked here. The struct does that. ## See also [Section titled “See also”](#see-also) * [Introspection reference](/adapters/introspection/) * [Avro](/adapters/avro/): the other binary format * [How adapters work](/adapters/how-adapters-work/)

# Actions as LLM and MCP tools

> Offer an action to a language model as a tool, with context fields the model never fills in and a single result shape for every outcome.

Preview `actionable-tools` sits at `1.0.0.pre1`. Its spec settles the behaviour, though no release has gone out yet. With `actionable-tools`, a language model can call an action as a tool. The action you already have, typed input, validations and declared failures and skips included, becomes the tool. Two things are left to you: a description, and a list of input fields your server supplies in place of the model, like the current user or tenant. The gem builds one neutral `Definition` and two thin wrappers, one for the MCP Ruby SDK and one for RubyLLM. Neither library is a dependency, and each is needed only by the require that uses it. 
```ruby
gem 'actionable-tools'
gem 'mcp', '~> 1.8'        # for actionable/tools/mcp
gem 'ruby_llm', '~> 2.1'   # for actionable/tools/ruby_llm
```
 
```ruby
require 'actionable/tools'
```
 Only what you name gets exposed. Nothing scans your actions and there is no registry, so each tool is built from one action class. ## The tool of an action [Section titled “The tool of an action”](#the-tool-of-an-action) The input schema is derived from the action’s `input` block through the [JSON Schema adapter](/adapters/json-schema/), with the context fields taken out. The model never sees a context field, so it can’t set one. 
```ruby
require 'actionable/tools'


class LogSounding < Actionable::Action
  input do
    required :gauge_code, :string, description: 'Stamped code of the tide gauge'
    required :region_id, :integer
  end


  output do
    required :entry, :string
  end


  fails :unknown_gauge, 'no such gauge', suggest: 'read the code off the housing'
  skips :already_logged


  step :record


  private


  def record
    skip!(:already_logged) if input.gauge_code == '7777'
    fail!(:unknown_gauge) if input.gauge_code == '0000'
    @entry = "Gauge #{input.gauge_code} sounded in region #{input.region_id}"
  end
end


tool = Actionable::Tools.definition(
  LogSounding,
  description: 'Log a sounding from a tide gauge',
  context: { region_id: ->(source) { source[:region_id] } }
)


tool.name                                # => "log_sounding"
tool.input_schema['properties'].keys     # => ["gauge_code"]
tool.input_schema['required']            # => ["gauge_code"]
```
 `description:` is mandatory, since the model picks tools by reading it. `context:` maps every hidden input field to a proc, and the proc receives whatever your server passes as the call’s source: a session, a token claim, an MCP server context. ## Context fields come from the server [Section titled “Context fields come from the server”](#context-fields-come-from-the-server) 
```ruby
reply = tool.call({ 'gauge_code' => '4821' }, { region_id: 3 })
reply['output']   # => {"entry"=>"Gauge 4821 sounded in region 3"}


sneaky = tool.call({ 'gauge_code' => '4821', 'region_id' => 999 }, { region_id: 3 })
sneaky['output']  # => {"entry"=>"Gauge 4821 sounded in region 3"}
```
 The model tried to pass `region_id: 999` and got ignored, because that value only ever comes from the context proc. If a context field names something the action doesn’t have, building the tool raises `ArgumentError`. Arguments still pass through `LogSounding.run`, so coercion and validation happen exactly as before. The schema only advises the model, and the action stays in charge. ## One result shape [Section titled “One result shape”](#one-result-shape) Success, failure or skip, every call hands back the same Hash with six keys, in this order. 
```ruby
ok = tool.call({ 'gauge_code' => '4821' }, { region_id: 3 })
ok.keys                             # => ["status", "code", "message", "output", "errors", "metadata"]
[ok['status'], ok['code']]          # => ["success", "success"]


missing = tool.call({ 'gauge_code' => '0000' }, { region_id: 3 })
[missing['status'], missing['code']]   # => ["failure", "unknown_gauge"]
missing['message']                     # => "no such gauge"
missing['metadata']                    # => {"suggest"=>"read the code off the housing"}


logged = tool.call({ 'gauge_code' => '7777' }, { region_id: 3 })
[logged['status'], logged['code']]     # => ["skipped", "already_logged"]
```
 A failure brings its declared code and metadata along, so the model can act on `suggest: 'read the code off the housing'` and try again. The tool’s `output_schema` describes the whole envelope, declared codes included, which tells the model what `unknown_gauge` might mean. Invalid input fails too, with the code `invalid_input` and the field errors. 
```ruby
bad = tool.call({}, { region_id: 3 })
[bad['status'], bad['code']]   # => ["failure", "invalid_input"]
bad['errors']                  # => {"gauge_code"=>["is required"]}
```
 ## A failure is an error and a skip is not [Section titled “A failure is an error and a skip is not”](#a-failure-is-an-error-and-a-skip-is-not) `error?` answers true only for a failure. A skip says there was nothing to do, and that is a fine thing to tell a model. 
```ruby
tool.error?(missing)   # => true
tool.error?(logged)    # => false
tool.error?(ok)        # => false
```
 An exception raised inside the action is not a result. It propagates, since this gem rescues nothing from the action, and your server decides how to report the bug. ## MCP [Section titled “MCP”](#mcp) `Actionable::Tools::MCP.tool` builds an `MCP::Tool` class for the MCP Ruby SDK. The server context plays the role of the call source. 
```ruby
require 'actionable/tools/mcp'


class ToFathoms < Actionable::Action
  input do
    required :feet, :float
    required :region_id, :integer
  end


  step :convert


  private


  def convert = succeed(fathoms: input.feet / 6)
end


mcp_tool = Actionable::Tools::MCP.tool(
  ToFathoms,
  description: 'Feet of depth to fathoms',
  context: { region_id: ->(server_context) { server_context[:region_id] } },
  annotations: { read_only: true }
)
server = MCP::Server.new(name: 'depths', tools: [mcp_tool], server_context: { region_id: 7 })


request = { jsonrpc: '2.0', id: 1, method: 'tools/call',
            params: { name: 'to_fathoms', arguments: { feet: 12.0 } } }
response = server.handle(request)


response[:result][:isError]                      # => false
response[:result][:structuredContent]['output']  # => {"fathoms"=>2.0}
mcp_tool.to_h[:annotations]                      # => {destructiveHint: true, idempotentHint: false, openWorldHint: true, readOnlyHint: true}
```
 The example drives the server object in-process, so no process starts and no client connects. * `annotations:` accepts `read_only`, `destructive`, `idempotent` and `open_world`. Any other key raises while the tool is built. * `isError` is set by a failure and not by a skip. * `content` and `structuredContent` hold the same JSON. * Arguments of the wrong type are rejected by the SDK before the action runs, for example a number sent for a decimal, which the schema calls a string. For a complete stdio server, see the gem’s `examples/stdio_server.rb`. ## RubyLLM [Section titled “RubyLLM”](#rubyllm) `Actionable::Tools::RubyLLM.tool` returns a `RubyLLM::Tool` subclass. Construct it with the object your context procs read, like the current user. 
```ruby
require 'actionable/tools/ruby_llm'


Surveyor = Struct.new(:id)


LlmTool = Actionable::Tools::RubyLLM.tool(
  ToFathoms,
  description: 'Feet of depth to fathoms',
  context: { region_id: ->(surveyor) { surveyor.id } },
  approval: true
)


llm_tool = LlmTool.new(Surveyor.new(7))
llm_tool.name                            # => "to_fathoms"
llm_tool.requires_approval?              # => true
llm_tool.call(feet: 12.0)['output']      # => {"fathoms"=>2.0}
```
 What comes back is the envelope Hash, and a failure is returned rather than raised. RubyLLM ignores `annotations:`. No model is involved, so the example stays inside the process. ## What is and isn’t covered [Section titled “What is and isn’t covered”](#what-is-and-isnt-covered) * An action with a discriminated input (`input_for`), or with no `input` block, raises `ArgumentError`. * A description stays mandatory until actions can describe themselves. * A `big_decimal` appears in the schema as a string like `"12.50"`. An `in:` range does not appear, but the action still enforces it. * Output is checked against the schema on success only. * Authentication, streaming and resources are not part of it. Those belong to your server. ## See also [Section titled “See also”](#see-also) * [JSON Schema](/adapters/json-schema/): where the input schema comes from * [Declare and handle outcomes](/how-to/handle-action-outcomes/): the codes a model reads * [How adapters work](/adapters/how-adapters-work/)
